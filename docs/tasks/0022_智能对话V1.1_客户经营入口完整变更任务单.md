## 0. 一页总览

### 0.1 为什么改

业务评审确认：大量授课老师为兼职人员，主要关注授课；店长/门店管理人员才是接待、客户跟进、周期回访与记录管理的主要使用者。因此 V1.1 从“先新增一条记录”调整为“**优先从客户列表选择客户，再发起接待记录**”。

本轮解决：

- 店长在首页快速找到**已到店 / 未到店、已成交 / 未成交**客户，围绕同一客户持续新增接待记录；
- 首页待提交任务看得见，但历史记录不挤占客户列表；
- 已有客户发起的新记录不允许在确认页改错、换错客户；
- 未预选客户时仍保留直接记录、后续补充信息的入口；
- 原录音、ASR、AI 结构化整理、人工确认等稳定能力继续复用。

### 0.2 本轮不做

不做新的完整 CRM、自动客资创建/合并、自动更新客户主档、智能跟进待办/提醒、成交状态自动判断、课程推荐、管理看板分析、员工权限重构、重训/更换 ASR 或 LLM、不改 Coze 结构化字段。

## 1. 全局业务与交互原则

1. **使用者定位：店长/门店管理人员优先**，授课老师并非必须完成复杂登记；继续支持其他获授权门店人员使用，权限不得擅改。
2. **客户为主、记录为辅**：首页给客户选择留最多空间；同一客户可有多条不同时间的接待记录。
3. **双路径并存**：A. 客户列表预选客户 → 新增接待；B. 底部直接新增 → 未预选客户。
4. **双采集模式不变**：面客模式 `face_to_face` 与事后补录 `post_recording` 继续共用 ASR → AI 整理 → 人工确认 → 保存的后半链路。
5. **两种信息来源分离**：CRM/客户列表既有客户主档信息与 AI 从逐字稿提取的新信息必须区分，不能互相静默覆盖。
6. **记录与客户关系可靠**：若从已有客户发起，客户唯一标识须在录音、整理、草稿、确认、提交、历史详情及后台查看的相关链路持续可追踪；仅展示客户姓名不算完成关联。
7. **业务状态来源可靠**：到店、成交状态取现有业务数据或明确标注 Mock 的现有数据；不得从 AI 总结自行改变状态。
8. **不伪造数据**：不加入“最近跟进”“近期回访”等当前未有可靠来源的字段；不臆造客户权限范围、客户类型。
9. **状态展示一致**：首页概览、待提交入口与完整历史记录页使用同一套记录状态口径。
10. **增量、可回滚、可验收**：先保留旧路由/旧页面实现，必要时以新增入口及适配逻辑替代；验收前不删除稳定能力。

## 2. 首页信息架构（P0）

### 2.1 页面顺序

```text
┌──────────────────────────────────────────┐
│  智能对话                                │
├──────────────────────────────────────────┤
│  接待记录                      [历史记录] │
│  全部 N     整理中 N   待提交 N  已提交 N │
├──────────────────────────────────────────┤
│  待提交记录                              │
│  待确认接待记录              N 条     >  │
├──────────────────────────────────────────┤
│  客户列表                                │
│  [搜姓名/手机]  [到店 ▾] [成交 ▾]        │
│  姓名 + 脱敏手机号            客户详情 > │
│  到店状态 / 成交状态         [新增接待]  │
│  ──────────────────────────────────────  │
│  更多客户……（列表滚动）                  │
├──────────────────────────────────────────┤
│            [+ 新建记录]（固定底部）       │
└──────────────────────────────────────────┘
```

上图是信息/交互示意，不是要求严格照字符对齐；视觉细节以最近确认的移动端参考图及当前奥本组件风格为准。

### 2.2「接待记录」概览与历史入口

- 标题为**接待记录**。
- 四项**仅展示数量和标签**：全部、整理中、待提交、已提交。
- 中性色、轻量字号、不要四种彩色块，也不要每项前的小图标；数字可比说明字略醒目，但整体弱化。
- 右上**历史接待记录**为可见、可点击的独立入口。可以只保留一个历史图标配简洁文案/箭头；**不显示“已提交 X 条”作为该按钮内容**。
- 点击后进入**完整历史接待记录页**，不是直接只看已提交。
- 概览数字是否可点：遵从既有能力；如新增按状态跳转，必须传正确筛选并可返回；不得让纯展示数字制造假交互。

### 2.3「待提交记录」

- 标题只能叫**待提交记录**，不要“待处理”。
- 简洁展示**待提交 N 条**和进入入口；无需“AI 已整理”“等待确认”等描述；标题/行前均不要多余图标。
- 点击进入待提交记录的筛选列表；若当前已有“单条直达”模式，先保留已验证行为，并确保多条时可选择具体记录。
- `N=0` 时显示轻量空状态，不占过多页面高度。
- **不能**把整理中、录音中、已提交、整理失败计作待提交。
- 按当前代码状态机，待提交固定为 `ready-for-review + draft`；整理中、整理失败、录音中和已提交不计入。

### 2.4「客户列表」

**视觉与布局**

- 客户列表是首页主体；紧凑列表而非大卡片；减少空白、分割线区分客户。
- 客户头像**全部去掉**。
- 「客户列表」标题减小，符合真实移动端页面层级。
- 姓名、脱敏手机号、到店状态、成交状态放在左侧主要信息区。
- 右侧有**独立客户详情入口**（文字/箭头即可）；新增接待按钮与详情入口要有明确距离和点击区域，防误触。
- 新增接待为高频主操作，采用奥本品牌强调色；不要大面积彩色统计或黑色主按钮。
- 不展示“最近跟进”及其他未经真实业务来源确认的文本。
- 目标是在典型 375px 宽屏下显著提升首屏可见客户数量，但不能牺牲点击区域/可读性。

**搜索和筛选**

- 同行放置「搜索客户 / 到店状态 / 成交状态」三个控件，宽度可适应窄屏。
- 搜索：客户姓名/手机号（手机号搜索使用授权数据逻辑；显示仍脱敏）。
- 到店筛选：全部、已到店、未到店。
- 成交筛选：全部、已成交、未成交。
- 搜索与两个筛选需**组合生效**；切换或清除任一条件时保持另两个条件。
- 无结果时提供简洁空状态和重置筛选能力（可沿用已有组件）。
- 真实字段值若比二态复杂，**先对齐现有业务定义**，不得擅自把“未明确/预约中”等归入已到店或未成交。
- V1.1 Demo 客户列表仅模拟分配给当前门店的客户；本轮不接 CRM 分配接口、不扩展到其他门店或集团客户。正式客户来源和权限仍由业务系统决定。
- 每个客户的到店/成交状态必须由与客户 ID 关联的课程完成记录和正式课程购买记录计算，不能从智能对话记录或 AI 内容推断。

**行操作**

- 点击「客户详情」→ 已有客户详情路由，传正确客户 ID，能返回智能对话首页。
- Phase 2 完成前，「新增接待」入口可以展示但必须明确保持未接通状态；不得丢弃客户 ID 后跳入直接新增流程。
- Phase 2 完成后，点击「新增接待」→ 以对应客户作为预选客户，进入新建接待流程。
- 详情入口不能与新增按钮互相覆盖、穿透或因父级行点击误触。

### 2.5 底部固定按钮

- 固定显示 **「+ 新建记录」**，用于未预选客户的补充路径。
- 不应与客户行“新增接待”产生身份歧义；与现有新建流程兼容。
- 固定底栏预留滚动安全间距，不能遮挡最后一条客户或筛选结果。
- 兼容 iPhone 底部安全区，正常键盘打开/收起时不遮挡搜索或交互。

### 2.6 视觉基线

- 功能原型不是宣传海报：模块标题、数字、状态徽标、按钮、间距按真实 H5 视口设计。
- 推荐验收宽度：320、375、390、430 CSS px；同时查看长内容/少内容状态。
- 强调色留给“新增接待 / 新建记录”和必要的待提交提示；概览均为中性色。
- 不强制另起一套设计系统；优先复用现有奥本移动端样式与组件。

## 3. 接待记录中心 / 历史记录（P0）

### 3.1 入口及页面复用

- 从首页「历史接待记录」进入独立列表页面，优先复用原先首页下半部的完整记录列表/筛选功能。
- 不要只展示已提交；应可查看**全部、整理中、待提交、已提交**，并保留现有异常/失败记录处理入口。
- 保留原有日期或时间范围筛选、必要的记录类型/模式等**已有能力**；未实现的筛选不要凭空宣称完成。
- 列表支持进入正确的记录详情或待确认页。

### 3.2 状态口径（已对照当前代码确认）

| 展示分类 | V1.1 口径 | 不应包含 |
|---|---|---|
| 全部 | 当前用户有权限查看的所有记录状态（含既有失败/异常） | 不应只等于后三项的硬编码相加 |
| 整理中 | 正在识别/整理、当前无法最终提交的记录 | 已可人工确认的草稿 |
| 待提交 | 已达到人工确认/提交条件，但尚未正式提交的记录 | 整理失败、录音进行中 |
| 已提交 | 已完成正式提交的记录 | 草稿/未提交 |
| 整理失败/异常 | 继续在“全部”中可见，并沿用原有重试/错误策略 | 不得悄悄丢弃或计入待提交 |

**当前实现映射：** `RecordStatus` 为 `processing`、`ready-for-review`、`failed`、`draft`、`submitted`；待提交=`ready-for-review + draft`。录音进行状态另由 `RecordingState` 表示，不计入待提交。失败继续在全部中可见。

### 3.3 状态操作

- 整理中：查看整理状态/沿用已有等待机制。
- 待提交：进入 AI 整理结果确认与提交；关联客户只读规则仍有效。
- 已提交：进入只读记录详情；后台沿用已提交记录查看规则。
- 失败：显示已有错误提示及重试能力（若已有），不得在本轮改掉失败生命周期。
- 若某条记录在页面上变更状态，概览、待提交数量、列表状态应同步体现（本地 Mock 或实际数据以原数据源更新方式为准）。

## 4. 双入口新建与客户关联（P0）

### 4.1 路径 A：预选已有客户（主要路径）

```text
首页客户列表 → 点击对应客户“新增接待”
→ 带入客户唯一 ID 及供展示的快照
→ 选择面客模式 / 事后补录
→ 录音/补录 → ASR 文本 → AI 整理
→ 人工确认页面（客户主档信息只读）
→ 保存草稿或正式提交
→ 接待记录关联该客户 ID → 历史/详情/后台正确展示
```

- **预选客户是唯一关联对象**。确认页客户区显示已选客户，不可编辑、不可换人；避免错误覆盖或替换。
- 路由参数/状态只作传递；**不可只依赖页面内存状态**，刷新、返回、重进草稿后的关联必须稳定。具体实现按现有存储/路由选择，不先锁定技术方案。
- `customerId` 是关联依据，姓名、手机号是展示快照，不应作为唯一标识。
- AI 从逐字稿提取的年龄、职业、身体情况等内容仍可以按既有结构化记录能力进行人工校正，**但不能写回/覆盖 CRM 客户主档**。
- 同一 `customerId` 可对应多条接待记录。
- 若预选客户失效/不存在/权限不可见，应提示并阻止静默绑定错误对象；具体回退处理沿用现有错误体验。

### 4.2 路径 B：直接新建（次要路径）

```text
首页底部“+ 新建记录”（无预选客户）
→ 选择面客模式 / 事后补录
→ 录音/补录 → ASR 文本 → AI 整理
→ 人工确认（允许补充/修改本条记录的客户信息）
→ 保存草稿或提交（沿用现有无绑定处理规则）
```

- 不预先携带 `customerId`。
- 确认页客户信息允许人工填写/编辑（以现有字段和保存规则为准）。
- 姓名/手机号相似**不等于**自动识别 CRM 客户；不得自动创建、合并、覆盖客户主档。
- 如果现有实现允许未绑定提交，则本次保持；若现有必须关联，则 Codex 应先报告冲突、等待业务确认，不擅自改变提交条件。

### 4.3 确认页客户信息锁定矩阵

| 内容 | 预选客户路径 A | 直接新建路径 B |
|---|---|---|
| 客户关联 ID | 固定，来自已有客户 | 初始为空；遵循现有提交机制 |
| 客户姓名/手机号/主档信息 | **只读展示** | **可按现有能力填写/修改** |
| AI 提取的接待分析模块 | 可按现有规则校正 | 可按现有规则校正 |
| 允许切换客户 | **不允许** | 不得暗中自动关联；如既有有显式选择行为则保留 |
| 保存草稿后再打开 | 原关联保持、仍只读 | 保留已输入内容与编辑能力 |
| 提交后 | 关联预选 `customerId` | 按既有无客户/手工填写记录规则 |
| 写回客户主档 | 不允许 | 不允许 |

### 4.4 必须回归的边界

- 面客/事后补录两种模式均支持 A、B 两条来源；
- 暂停、返回、取消、重新进入、保存草稿、页面刷新、提交成功/失败后的关联逻辑不能丢失；
- 不得因客户卡片展示更新而将已录入记录意外绑定其他客户；
- 客户字段与 AI `basic_info` 在确认页需要清楚区分信息来源；
- 录音并发限制、悬浮控件、异常提醒、整理进度不得被修改。

## 5. 记录详情与后台兼容（P0）

1. 首页/历史记录详情可以展示本条接待记录的客户关联情况。
2. 预选客户记录：显示正确客户，支持已有客户详情跳转（如果现有模块已有）。
3. 直接新建记录：未绑定时按原有展示规则处理，不伪造客户 ID。
4. 已提交与待提交：遵守现有只读/可编辑边界，已提交记录不得再次以草稿表单修改。
5. 后台 `#/admin/dialogue-records` 及详情等既有入口（以阶段0实测路由为准）应继续正常；仅已提交记录可出现在原“正式记录后台”管理列表，除非现有规则另有明确规定。
6. 客户绑定状态必须反映真实关联，不再所有数据都错误显示“未关联”；Mock 则明确 Mock 条件。
7. 这不是“新增后台运营分析/CRM跟进待办”项目；不要顺带扩展。

## 6. 已确认业务口径与 Mock 规则

本节为产品最终确认的 V1.1 规则，优先于本任务单中较早版本的待确认表述。

| 事项 | V1.1 最终口径 | 依据/边界 |
|---|---|---|
| 客户列表范围 | 只展示分配给当前门店的客户 | Demo 用 StoreContext 和 Mock 模拟；不接正式分配接口、不跨店展示 |
| 已到店 | 至少存在一条有效且已完成的体验课或正式课下课记录 | 预约、购买但未上课、取消、接待记录或 AI 判断均不算 |
| 已成交 | 至少存在一条有效正式课程购买记录 | 体验课购买不算；正式课购买后尚未上课也算；不从到店或接待意向推断 |
| 两类状态 | 到店和成交分别由客户 ID 关联的 Mock 课程完成/正式课购买记录计算 | 不使用 `visited=true`、`converted=true` 作为独立硬编码结果；本轮不设计退款/撤销规则 |
| 待提交 | `ready-for-review + draft` | `processing`、`failed`、录音中、已提交不计入 |
| 客户详情 | 复用 `#/member-center/members/:id` | V1.1 Demo 客户均有稳定 member ID 与 customer ID 映射；不开发通用 CRM 客户详情 |
| 直接新增 | 完全保持 V1.0 的手机号查询、客户信息、关联及保存/提交校验 | 不允许未关联提交；不放宽、不加强既有校验 |
| 客户关联 | 同一客户可有多条接待记录；预选客户通过稳定唯一 ID 关联 | 姓名和手机号仅作快照；AI 内容不写回会员主档 |
| 客户权限 | 只用现有门店上下文和 Mock 归属模拟 | 不扩展角色权限或正式客户授权模型 |
| 首页统计 | 当前门店全部记录，不受历史页时间筛选影响 | 全部包括失败；与 ReceptionRecords 同源 |
| Mock 持久化 | 客户/会员 ID 稳定，刷新后可继续定位会员详情 | 兼容现有记录；V1.1 与 V1.0 使用不同端口和 localStorage |

正式客户数据来源、课程系统和订单系统仍需未来业务系统提供；这不阻塞本轮自洽的 Demo Mock 实施。

## 7. 开发实施原则（仅供 Codex，技术说明独立于业务需求）

### Phase 1｜首页布局与现有入口（P0）

**工作内容**

- 实现接待记录标题、四项轻量统计、历史记录入口；
- 实现简化待提交数量；
- 实现客户列表紧凑布局、去头像/虚假最近跟进、同行搜索+到店+成交筛选；
- 保留右侧独立客户详情和避免误触的新增接待操作；
- 固定底部直接新建按钮；
- 状态概览与列表使用一致来源/口径；不决定尚未明确的跨店客户权限；
- 历史记录入口阶段内允许先路由到旧完整记录页，不能假链接。

**验收**

- 320/375/390/430 宽度布局无溢出，列表可滚动、底栏不遮挡；
- 搜索和两个筛选可组合执行；客户详情/新建按钮互不误触；
- “待提交”不夹带整理中/失败；数值跟列表一致；
- 5173 旧版未变；V1.1 原录音链路未改。

**停止条件**：完成后提供截图/访问地址、变更文件和测试结果，停下等首页视觉验收。

### Phase 2｜预选客户新增 + 关联贯穿（P0）

**前置**：Phase1 产品通过；第 6 章客户来源/唯一 ID 取得足够依据。

**工作内容**

- 客户列表行“新增接待”传递 `customerId`；
- 进入模式选择（面客/事后补录），再流向原有录音/AI 整理；
- 预选客户信息随记录流转，草稿/刷新/恢复不丢；
- 直接新建不携带客户 ID，继续原路径；
- 尽量通过共享上下文/记录持久层复用逻辑，不复制两套链路。

**验收**

- A/B × 面客/事后补录 四组路径全部能走到 AI 确认；
- `customerId` 在草稿、确认和未来提交数据中一致；
- 直接新建无意外客户绑定；
- 取消/返回/重新进入后不串客户；
- 原录音与 ASR 功能无回归。

**停止条件**：列出关联链路证据和测试结果，等待确认进入 Phase 3。

### Phase 3｜确认提交：已选客户只读 / 直接新增可编辑（P0）

**前置**：Phase2 通过。

**工作内容**

- 客户预选路径：确认页的客户主档信息只读、不可修改、不可换人；AI 整理的接待信息保持现有人工修正能力；
- 直接新增路径：客户信息按现有能力可填写修改，不自行 CRM 自动匹配；
- 草稿保存/恢复保持上述权限和信息来源；
- 提交成功后正式记录保存关联 ID，并刷新记录状态；
- 校验失败/未成功提交时不得虚假标为已提交。

**验收**

- 已选客户信息无法编辑，但 AI 接待内容仍能编辑；
- 直接新增客户信息仍可编辑；
- 草稿重开锁定规则保持；
- 提交后关联不丢，待提交统计减少，已提交/历史可查看；
- 无隐式覆盖 CRM 主档。

**停止条件**：等待产品走查确认页及完整提交。

### Phase 4｜完整历史记录中心与详情（P0）

**前置**：Phase3 通过。

**工作内容**

- 历史入口打开原完整记录列表能力，保留原筛选/日期及整理中、待提交、已提交、失败等状态；
- 审核首页 4 项数量、待提交条数与完整历史记录统计；
- 整理中、整理失败保留原交互；待提交进入确认；已提交只读；
- 记录详情显示预选客户的正确关联或未绑定状态。

**验收**

- 各状态记录均可找到，失败记录不会被藏没；
- 状态变更后统计一致；
- 原已有历史列表能力没有回退；
- 新旧记录详情兼容，未绑定记录可正常查看。

**停止条件**：验收历史记录与详情后才进入 Phase 5。

### Phase 5｜后台兼容及全链路回归（P0）

**前置**：Phase4 通过。

**工作内容**

- 检查后台已提交记录列表/详情；
- 验证新记录正确关联客户，旧 Mock / 旧记录兼容；
- 确认后台仍只展示正式已提交记录（按现有规定）；
- 回归录音、悬浮条、暂停/结束、ASR、AI 整理、确认、异常恢复和双入口；
- 执行 typecheck、build、test 及可运行的 lint；新增必要自动化测试；
- 核查 5173 与 V1.0 Tag 未受影响。

**验收测试集（至少覆盖）**

1. 预选客户 A → 面客 → AI → 草稿 → 重开 → 客户锁定 → 提交 → 历史/后台关联 A。
2. 预选客户 B → 事后补录 → AI → 只读 B → 提交；不串到 A。
3. 直接新增 → 面客 → 客户信息可编辑 → 提交；不自动绑定 CRM。
4. 直接新增 → 事后补录 → 保存草稿 → 恢复可编辑。
5. 待提交/整理中/已提交/失败分别出现时，统计、筛选、入口正确。
6. 客户姓名/手机号搜索 + 到店/成交组合筛选 + 无结果。
7. 客户详情与新增接待点击热区独立；窄屏不误触。
8. 返回/刷新/无效 customerId/提交失败路径不造假、不丢记录。
9. 旧历史记录仍可打开，后台不出现未提交草稿。

**停止条件**：全链路测试通过、业务已验收、无 P0 阻塞后，才可以另开“版本合并/发布”任务；本任务本身不执行 merge/push/deploy。
